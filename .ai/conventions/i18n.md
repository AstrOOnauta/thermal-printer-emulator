# i18n

Three locales: **English (default)**, **Spanish** and **Brazilian Portuguese**. Every
user-facing string lives under a stable key, in all three.

## Where the locale comes from

Rust decides it in `src-tauri/src/locale.rs`, and both sides use that value:

- the `language` setting (`flows/settings.md`): `system` (default), `en`, `es` or
  `pt-BR`, applied with `Locale::prefer` (a process-wide `AtomicU8`) at startup, before
  any native menu is built, and on every change;
- for `system`, the OS language (`sys-locale`), read once per process (`Locale::system`).

`Locale::current()` combines them. The native tray and macOS menu read
`Locale::current().strings()`; the webview calls `app_locale` in `initLocale()`
(`main.tsx`) **before the first render**, so text never flips.

**Changing the language at runtime**: `set_settings` calls `Locale::prefer`, then
`shell::refresh_menus` rebuilds the tray menu (with the current status line) and the macOS app
menu. The webview asks `app_locale` again (Rust resolves `system`), calls `setLocale`, and
re-renders from `App`, which re-runs every `t()`. No restart.

`Locale::from_tag` takes the language subtag of a BCP 47 or POSIX tag: `pt*` → `pt-BR`,
`es*` → `es`, anything else (including `C` and empty) → `en`. It is unit tested.

The webview does not use `navigator.language`: WKWebView on macOS does not reliably follow
the system language, and the window would then disagree with the tray.
`Info.plist` declares `CFBundleLocalizations` (en, es, pt-BR) so macOS also localizes
system-provided UI.

Outside Tauri (`yarn dev` in a browser) the command fails and the UI stays in English.

## Webview

- `src/shared/translations/en.ts` is the **source of truth**: it exports the object and
  `type TranslationKeys = typeof en`. `es.ts` and `pt-BR.ts` are typed `: TranslationKeys`,
  so a missing or extra key fails `yarn typecheck`.
- `src/shared/hooks/use-translation.ts`: `const { t } = useTranslation(); t('app.name')`.
  Typed dot notation (`TranslationScope`) and `%{var}` interpolation. An unknown key
  renders as the key itself.
- The active locale is a module-level value (`setLocale` / `getLocale`); changing it
  re-renders from `App` (a state bump), so there is no store. Components must not memoize
  translated text.

## Native menus (Rust)

Tray and macOS app-menu labels are the `Strings` tables (`EN`, `ES`, `PT_BR`) in
`locale.rs`, because the webview cannot translate a native menu. The app menu's labels sit
in `Strings::menu` (`MenuStrings`), compiled on macOS only: elsewhere they would be unused,
which `-D warnings` turns into a build error on Linux and Windows. Same wording rules as the
webview. The listener status line uses a `{port}` placeholder, filled by
`shell::status_label`; keep it in sync with `listener.*` in the TS files.

## Rules

- **No hardcoded user-facing strings** in TSX: labels, placeholders, aria text and errors
  all go through `t()`.
- Text that Rust sends to the webview is a **key** with params, never a sentence.
- Adding a language means one TS file, one `Strings` table, a branch in
  `Locale::from_tag`, a `Language` variant (and its `AtomicU8` value), an entry in the
  settings screen's `LANGUAGES` list (its own name), an entry in `CFBundleLocalizations`,
  and the NSIS `languages` list in
  `tauri.conf.json`.
- Copy is short and plain. The product name "Thermal Printer Emulator" is never
  translated.
